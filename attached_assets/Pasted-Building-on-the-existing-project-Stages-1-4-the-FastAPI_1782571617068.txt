Building on the existing project (Stages 1-4 — the FastAPI backend at api/main.py
is already running and exposes /api/runs endpoints, with a static-file catch-all
route already in place), build the frontend for Silver Bullet: a polished,
distinctive web UI, not a generic admin dashboard template.

PART A — Setup
- Use React + Vite + Tailwind CSS in a /frontend folder.
- Configure vite.config.js's build.outDir to point directly at ../api/static, so
  running `npm run build` produces output FastAPI already serves — no manual
  copy step needed.
- Poll GET /api/runs and GET /api/runs/{job_id} every 3-5 seconds for any job
  whose status is not yet completed or error. Stop polling a job once it reaches
  either of those terminal states. Do not use websockets — this app doesn't need
  that complexity.
- "Open New Case" should let the user either leave disease blank (backend
  auto-picks the top candidate) or type a specific disease name, matching the
  optional disease_name field POST /api/runs already supports.

PART B — Design direction (follow this exactly — no purple gradients, no generic
card-grid dashboard, no giant hero stat numbers, no default Tailwind component
library look)

This app is the digital equivalent of a case dossier, not a metrics dashboard,
because that's what it actually produces: an evidence-backed hypothesis with
citations, not a live KPI feed. Lean into that throughout.

Color tokens (CSS custom properties, use exactly these):
  --graphite: #1C1D21   (page background)
  --paper:    #EDE8DF   (card/content surfaces — warm, slightly aged paper)
  --silver:   #C7CAD1   (primary accent — borders, active states, used sparingly)
  --brass:    #C08A35   (positive signal — STRONG_MATCH, "approve")
  --oxide:    #9B4A3F   (caution signal — limitations, "reject," errors)
  --ink:      #2A2B2E   (body text on paper surfaces)

Type tokens (load via Google Fonts):
  - Display face: a high-contrast slab/serif (Fraunces or Spectral) — page title
    and case-status headers only
  - Body face: a clean humanist sans (Inter or Source Sans) — all prose
  - Data face: a real monospace (JetBrains Mono or IBM Plex Mono) — every PMID,
    ChEMBL ID, NCT number, score, and disease/target name in tables. This is
    functional: it makes identifiers visually distinct from prose at a glance,
    not decoration.

Layout concept:
  - Dashboard/home: past and in-progress cases shown as a row of file-folder
    tabs (not a card grid) — each tab labeled with disease name, status badge,
    date, and running cost (from GET /cost). Clicking one opens the case. A
    clearly visible "Open New Case" action starts a new run.
  - Live case view: a vertical stepper showing the REAL pipeline sequence —
    Target Selection, Biologist, Chemist, Reviewer, Structure Validation,
    Writer, Awaiting Review — current stage highlighted in --brass, completed
    stages checked off. This sequence is earned here since it reflects real
    progress, not a decorative numbered list.
  - Awaiting-review view: the full compiled report inline (evidence table,
    citations, limitations section, composite score breakdown), with two
    actions at the bottom framed as a literal sign-off: "Approve case" (brass)
    and "Reject case" (oxide), each requiring a short typed note before it
    confirms. Frame this explicitly as the human review checkpoint, not a
    generic form.
  - Completed report view: same dossier layout, plus a circular stamp element
    (pure CSS/SVG, not an image — roughly 120px, irregular hand-stamped-looking
    border, text rotated about -8deg, wide letter-spacing, small caps, ~85%
    opacity to look inked rather than printed) reading "STRONG MATCH" (brass) or
    "REJECTED" (oxide) depending on outcome.
  - Error state: if a job's status is "error," show its error_message in an
    oxide-toned panel, not a generic red bootstrap alert.

Copy/voice rules:
  - Never imply a cure was found. Use "hypothesis," "candidate," "evidence,"
    "requires wet-lab validation" — this system produces a falsifiable
    hypothesis, not a finding, and the UI's language has to reflect that
    honestly even in success states.
  - Buttons say exactly what they do: "Open new case," "Approve case," "Reject
    case" — never "Submit" or "Go."
  - Empty states read as an invitation to act, not an error: "No cases yet —
    open one to start," not "No data found."

PART C — Accessibility and responsiveness baseline
  - Responsive down to mobile width
  - Visible keyboard focus state on every interactive element
  - Respect prefers-reduced-motion for any transitions/animations
